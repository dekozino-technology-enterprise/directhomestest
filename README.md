# Direct Homes: direct-rental platform for Nigeria

Landlords and managers list verified properties; tenants search, contact the owner, get a payment token and pay the owner's bank account directly. No agents, no viewing fees. Owners pay one yearly onboarding fee per property after verification. Maintenance, reviews, reports and analytics are included.

```text
directhomes/
├── backend/          Node.js 22 + Express + TypeScript + Prisma + PostgreSQL API
│   ├── prisma/       schema.prisma, migrations/, seed.ts, rls.sql
│   ├── src/          routes/, lib/, jobs/, middleware/, server.ts
│   ├── tests/        end-to-end scripts (phase5, phase6)
│   ├── .env.example  local configuration template
│   └── Dockerfile
├── frontend/         static web app for tenants, owners, managers, admins (Netlify)
├── render.yaml       free Render demo Blueprint
└── .github/workflows/ci.yml and docker-image.yml
```

## Run locally

Use Node.js 22+ and a **development** PostgreSQL database. Copy `backend/.env.example` to `backend/.env` and replace the placeholders; never commit `.env` or use production secrets in a development environment.

```bash
cd backend
npm ci
npx prisma migrate dev
npm run db:seed                 # admin user, unit types, features, fee tiers, Lagos
npm run dev                     # http://localhost:4000/api/health
```

Admins sign in on the same login page as everyone else; the admin area is in the web app under the Admin menu. Then serve `frontend/` (see `frontend/README.md`). If you do not use a terminal on your computer, GitHub Codespaces provides a browser-based development terminal.

## Test deployment (free Render + Supabase + Netlify)

The repository includes a baseline migration for the current Prisma schema. **Keep `backend/prisma/migrations/` in Git.** The free-test Blueprint runs migrations and the idempotent seed at process startup, so it does not need Render's paid-only pre-deploy step or Shell access.

1. **Supabase:** create a project and Storage buckets `listing-photos` (public) and `private-files` (private). Use the Transaction pooler URL (port 6543, `pgbouncer=true&connection_limit=1`) for `DATABASE_URL`, and the Session pooler URL (port 5432) for `DIRECT_URL`. After the first migration, run `backend/prisma/rls.sql` in the Supabase SQL Editor; repeat after migrations add tables.
2. **Render:** create a Blueprint from a repository you can deploy (your fork is easiest; see below) and apply `render.yaml`. It is set to the **Free** plan, `NODE_ENV=development`, and has no Paystack/SMS/email keys configured. Enter the environment variables below. The first service start migrates and seeds the database; the seed is idempotent and runs again after a free-instance sleep/restart.
3. **Netlify:** import the same repository, set **Base directory** to `frontend`, leave the build command empty, and set the publish directory to `.`. Replace `YOUR-API` in `frontend/netlify.toml` with the Render hostname before deploying. Leave `frontend/config.js` unchanged; Netlify proxies `/api` and `/media` to Render.
4. Set Render's `WEB_ORIGIN` to your Netlify site origin (no trailing slash). This controls CORS.

For this demo configuration, OTP codes are printed in Render logs when no provider is configured. With no Paystack key, the API enables its development-only payment simulation. **Do not use this configuration for real users or production.** The web service sleeps after 15 minutes without traffic, can take about a minute to wake, and its in-process scheduled jobs pause while asleep. Supabase holds the database and uploaded files; the Render filesystem is temporary. The frontend now downloads a smaller WebP hero image and parallelizes dashboard/onboarding API requests, but it cannot remove Render Free's idle cold start.

### Environment variables

| Variable | Value / purpose |
|---|---|
| `DATABASE_URL` | Supabase Transaction pooler; port 6543, `pgbouncer=true&connection_limit=1` |
| `DIRECT_URL` | Supabase Session pooler; port 5432; Prisma uses it for migrations |
| `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `HASH_PEPPER` | Generated by `render.yaml` |
| `DATA_ENC_KEY` | Exactly 64 hex characters (32 random bytes). For a browser-only GUI generator, open `tools/data-enc-key-generator.html`; paste into Render → `house-mgmt-api` → Environment. Keep it private and backed up; never replace an existing valid key or change it after accounts are saved, or encrypted numbers may become unreadable |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | Initial admin credentials; used by the seed |
| `WEB_ORIGIN` | Your Netlify origin; comma-separate additional allowed origins |
| `SUPABASE_URL`, `SUPABASE_SERVICE_KEY` | Supabase project URL and server-side secret key; never put the key in frontend code |

Paystack, Termii, and Resend are intentionally **not** included in the free-test Blueprint. Add them only when you are ready to test those integrations. Paystack is for the yearly property onboarding fee; tenant rent is paid directly to the owner/manager by bank transfer.

### Do I need to fork?

Render does not require a fork just because you are deploying a Blueprint. But the upstream repo's `render.yaml` sets `plan: starter` (paid), and the original upstream branch lacked the migration files needed by its migration command. You cannot change those files on Kozino's repo. To use the free-test configuration and the fixes in this copy, deploy a fork or your own copy. You can use the `main` branch of your own fork; you do not need to create a separate branch.

### Moving from test to production

Do not simply switch `NODE_ENV` to production while keeping the demo startup command. For production, use a paid always-on plan, set `NODE_ENV=production`, move `npx prisma migrate deploy` to Render's pre-deploy command, use `npm start` as the start command, and run the seed once from the Render Shell. Configure Supabase Storage, a real OTP provider, and (if taking yearly fees) Paystack before launch. Review the seeded fee tiers—they are placeholders.

For future schema changes, use `npx prisma migrate dev --name <change_name>` against a development database and commit the generated migration files. Never run `migrate dev` against production.
